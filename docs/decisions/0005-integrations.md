# ADR 0005: Integrations (M5)

**Status:** accepted for M5 · 2026-09-29

## Decisions

1. **Connections are data, credentials are write-only.** `integration_connection` holds one live connection per provider per company (partial unique index). Credentials are encrypted with AES-256-GCM (`app/core/crypto.py`). The key ring comes from `INTEGRATION_KEYS`: the first key encrypts and every key decrypts, so keys can be rotated. The connection ID is the associated data, so a ciphertext copied onto another row does not decrypt. The API only ever reports `has_secret`. Validation errors never echo submitted values. The audit trail records "secret changed: yes/no" and nothing more. Staging and production refuse to start without `INTEGRATION_KEYS`, and without keys the API returns 503 instead of storing plaintext.
2. **A connection receives data only after a passed test.** Saving puts it in `NEEDS_TEST` and queues `integration.test`. Tests read metadata only: the Sheets header, the Power BI model, and the Mail.Send role in the Graph token. A pass makes it `CONNECTED` and re-sends every approved record, because the destination may have been replaced. A test result is discarded if the configuration changed while it ran (`config_version`).
3. **States:** `NEEDS_TEST`, `CONNECTED`, `TEST_FAILED`, `RECONNECT_REQUIRED` (401/403/404 or unreadable credentials), `CONFLICT` (destination changed in a way we must not overwrite) and `DISCONNECTED`. Disconnecting erases the ciphertext, cancels queued jobs and keeps the history.
4. **Adapter contract** (`app/integrations/base.py`): every provider answer maps to a stable code plus one consequence: transient (retry with backoff, honouring `Retry-After`), reconnect, or conflict. Provider response bodies are never stored or shown.
5. **Delivery path:** `production_record.changed` (already in the outbox since M3) → `integrations.fanout` (coalesced per record) → `record_sync` rows `PENDING` for each connected record destination → one coalesced `sheets.sync` / `erp.sync` per destination. `record_sync.target_revision` only grows (`GREATEST`), so a late event cannot roll a destination back. A row becomes `SYNCED` only if it was not changed while the push ran.
6. **Job ledger additions:** `ensure_job` reuses a not-yet-started job for the same (kind, object), otherwise it opens the next generation (serialised by an advisory lock). `claim_next` never starts a job while another generation of the same (kind, object) holds a live lease. Together these give **one writer per destination**.
7. **Google Sheets:** row identity is `record_id`. Each run reads the header and all keys before writing. An empty tab gets the header. A different header (`SCHEMA_MISMATCH`) or a duplicated key (`DUPLICATE_KEY`) stops the connection as `CONFLICT` with nothing written. Existing rows are updated in place (`values:batchUpdate`); new rows are appended (`:append`, `INSERT_ROWS`). All values are sent with `valueInputOption=RAW`, so text such as `=SUM(A1)` stays text. A row holding a newer revision than ours is left alone and the record is marked `CONFLICT/DESTINATION_NEWER`. Because keys are read first, an append that timed out after landing is never duplicated (TC27).
8. **Power BI pulls; we only refresh.** Power BI imports `approved_production_v` and `production_watermark_v`. These views show only the companies mapped to the connecting database login in `bi_access` (`current_user`), so a BI login cannot read another company even though the views bypass per-request RLS, and it cannot read any table. `app.cli bi-access` creates such a login. Refreshes are coalesced: at most one per `min_interval_minutes`, with later requests folded into one deferred job; status is then polled. **Freshness** is FRESH only if a completed refresh covers the current `data_version` and is younger than `stale_after_minutes`. The native dashboard never waits for it.
9. **Microsoft Graph mail** is configured and tested in M5 (app-only token, Mail.Send role present). Nothing is sent until M6. Restricting the application to the sender mailbox (Exchange application access policy) is an administrator task this test cannot verify.
10. **ERP (A5):** no vendor is named in the specification, so M5 ships the `ErpAdapter` protocol, the append-only `erp_sync_attempt` ledger (with `mapping_version`), and `MockErpAdapter`. The mock is refused in staging and production and labelled "development only" in the UI. Only OUTBOUND is accepted; bidirectional sync needs an approved conflict policy first. ERP connections also require the `erp_integration` feature flag.
11. **Testing without credentials:** adapters run unchanged against `tests/fake_providers.py` (httpx `MockTransport` imitating the documented REST calls) via `app.integrations.set_transport`. Per the spec, these are adapter tests, not staged integration tests; live verification needs real accounts.
